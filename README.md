# Pi MCP Events

`@sanity-labs/pi-mcp-events` adds MCP Events to unmodified Pi: discover event types, subscribe through polling, streaming, or signed webhooks, and receive observations in the conversation. It registers no tools. Application-specific behavior belongs in separate extensions.

**Private iteration:** this repository is private and npm publishing is disabled. Install from a local checkout or tarball. Public distribution will be a separate release decision.

The package targets MCP revision **2026-07-28** and [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415) at `b0efd116faca84c9caad109ccf0778da4dc49579`. The [pinned draft](docs/events-draft.md) is included. Compatibility is tested with **Pi 1.4.0 and Node 24.21.0**; a draft update may require coordinated client/server changes.

## Install for iteration

```sh
mise install
mise exec -- npm ci
mise exec -- npm run validate
pi install "$PWD"
```

To share a built archive privately, run `npm pack`, then install it into a local directory with npm and register that directory with Pi:

```sh
npm install --prefix /absolute/path/to/iteration --legacy-peer-deps /absolute/path/to/sanity-labs-pi-mcp-events-0.0.0.tgz
pi install /absolute/path/to/iteration/node_modules/@sanity-labs/pi-mcp-events
```

Pi treats a bare local `.tgz` path as a resource path; npm must unpack it first.

`npm run validate` runs type checking, unit/protocol tests, and a clean tarball installation in stock Pi. It needs npm registry access and OpenSSL, but no Mellon checkout, cloud account, model API, or public tunnel. Build output is generated by `npm ci` and `npm pack`; it is not committed. Run `npm run build` after editing source when loading this checkout locally.

## Configure

Set `PI_MCP_EVENTS_CONFIG` to an absolute JSON path, or create `.pi/mcp-events.json` in Pi's working directory:

```json
{
  "servers": {
    "example": {
      "transport": "http",
      "url": "https://example.org/mcp",
      "headers": {"Authorization": {"env": "MCP_TOKEN", "prefix": "Bearer "}}
    }
  },
  "watches": [
    {"id": "changes", "server": "example", "name": "example.changed", "mode": "push", "arguments": {"channel": "demo"}}
  ]
}
```

Event names and arguments above are examples. The server must advertise the pinned Events extension and the selected delivery mode. The extension validates arguments and incoming payloads against its event catalog. It owns separate MCP connections; it does not reuse Pi's built-in MCP configuration or add ordinary MCP tools.

HTTP connections accept configured headers. Stdio connections use `transport: "stdio"`, `command`, and optional `args`, `cwd`, and `env`. Environment references work in HTTP headers and stdio environment values. Relative configuration paths resolve from the configuration directory. Interactive OAuth login and token refresh are not included; supply credentials through environment references or the server's stdio launcher.

For webhooks, add a `webhook` object with `publicUrl`, `host`, and `port`. `publicUrl` must be reachable HTTPS. Either provide `keyFile` and `certFile` for direct TLS, or put a trusted HTTPS proxy/tunnel in front of a loopback HTTP listener. Each watch gets its own callback path and signing secret. The receiver verifies signatures over the raw body and rejects stale requests. No hosted relay is included.

```text
/mcp-events list [server]
/mcp-events watch <server> <poll|push|webhook> <event> [JSON arguments]
/mcp-events stop <watch-id>
/mcp-events status
/mcp-events flush
```

Configured watches start with the session. Interactive watches are not saved. Renaming a configured watch starts a new cursor history; obsolete checkpoints are removed when a session starts. Incoming observations wait while the agent is busy or compacting, then become batched follow-up messages. They are untrusted data and do not authorize actions. `/mcp-events flush` retries pending delivery; manually flushing an already queued batch can produce duplicates.

## Sessions and delivery

Saved sessions persist the bounded inbox and checkpoints in `~/.pi/agent/mcp-events` (override with `stateDir`). State is scoped to the configuration path and Pi session ID; each watch keeps a separate cursor for its server configuration and delivery mode. The inbox is acknowledged only after the batch appears in Pi's session file. Resuming that session restores its cursors; replay depends on the server and event type.

With `--no-session`, events, cursors, and pending batches live only in memory, just like the conversation. The extension does not read or write event state files. Connection recovery can use the current cursor while the session is active; restarting starts fresh.

Shutdown stops polling, closes streams, and unsubscribes webhooks. After a crash or failed unsubscribe, the server's granted TTL bounds webhook lifetime. Ephemeral sessions always request a finite TTL, even if configuration specifies `ttlMs: null`.

Consumers must tolerate duplicates. Deduplication, retry queues, and the inbox are bounded; this is not an exactly-once guarantee. The inbox holds at most 100 observations or 256 KiB. Each server supports up to 32 active watches; a session retains up to 512 checkpoints. Cursors, retention, and gap reporting depend on the source. A null-cursor source cannot replay missed events.

## Extend and contribute

The experimental client API is exported from `@sanity-labs/pi-mcp-events`. Separate Pi extensions can observe the typed `mcp-events:observation` event without coupling to client internals. See [architecture and API](docs/architecture.md) for the boundaries and [development](docs/development.md) for testing, PRs, and the future release path.

All implementation changes go through pull requests. No direct pushes to `main`; the required `validate` check must pass. The initial PR retains separate protocol, delivery, session, and integration commits for review.
